## 一、背景与目标

阿奇锁的「虚拟资源发货」本质是：**当识别到一笔新的待发货订单时，自动以客服身份（IM）给买家发一条消息**，消息内容是预先配置好的卡密 / 固定文案 / 链接，而不是去点官方后台的「物流发货」按钮。

本文档从反编译产物（`tools/_agiso_strings/` 下从各 DLL 提取的字符串、以及内嵌资源 `IMSend.js`）审计出阿奇锁的真实链路，并以「需求」形式描述，供本仓库（`xhs-shipping-assistant`）对标实现。

### 2.4 客户端「发消息」核心脚本（IMSend.js，内嵌于 DLL 资源）

阿奇锁把一段 JS（`IMSend.js`）作为资源内嵌，登录后通过 CefEx 注入到小红书客服工作台页面（`walle.xiaohongshu.com`），页面里已有小红书官方 `window.XhsRim` IM SDK。脚本通过 `AcMain.taskResult(taskId, ...)` 把结果回传给 .NET 主进程。

核心调用如下：

```js
// 1) 订单号 → 买家（客户 ID）
//    通过页面 SDK rimSdk.getChatInfo 的参数拼装
const arg1 = {
    promoterType: 'OFFICIAL',
    invitedRefId: buyerId,               // 买家 id
    promoterType: window.ImLoginInfo?.csProviderId,  // 客服/商家 id
    additionInfo: { version: this.chatSdkVersion }
};
const arg2 = {
    receiverAppUid: `1#2#2#${buyerId}`,
    creatorParentAppUid: `1#3#6#${window.ImLoginInfo?.csProviderId}`,
    bizType: 'chat'
};
const chatInfo = await window.XhsRim.rimSdk.getChatInfo(arg1, arg2);
// chatInfo.data.id 即 chatId

// 2) 发送文本消息（卡密/文案/链接）
const r = await window.XhsRim.sendTextMsg(content, { chatId });

// 3) 发送图片消息
const imageFile = new File([blob], 'PC-IMG-' + Date.now(), { type: 'image/png' });
await window.XhsRim.sendImageMsg(imageFile, { chatId });

// 4) 自定义消息（content_type 73=视频 / 92=笔记）
await window.XhsRim.sendCustomMsg({ content, content_type: 73 }, { chatId });
await window.XhsRim.sendCustomMsg({ content, content_type: 92 }, { chatId, manualInsertFn });
```

配套的签名与请求头（页面内直接 fetch 小红书 API）：


## 三、需求分解（对标本仓库实现）

### 需求 1：订单识别（多通道）

| 项 | 阿奇锁 | 本仓库实现 |
|---|---|---|
| 云推送 | `xhsmsgwebsocket.agiso.com`（阿奇私有云） | `websocket.service.ts` 已留 `wss://xhsmsgwebsocket.agiso.com`（`DEFAULT_WS_URL`），`handleMessage` 处理 `order/order_paid/new_order` |
| 客服 WS | `zelda.xiaohongshu.com/websocketV2` | `connectKefu()` 已实现 |
| 页面 API 轮询 | `fulfillment/order/page` | `autoship.service.ts` 轮询 + `im-send.js` 的 `fetchPendingOrders` |
| 页面拦截 | 请求拦截 JS 过滤器（XhsJsFilter） | `api-interceptor.js` 拦截 `fulfillment/order/page` 响应，`postMessage('xhs-new-order')` |

**验收**：任一新待发货订单，能从上述任一通道被捕获，并携带 `order_id`、`product_id`（商品 ID）、`status`。

### 需求 2：商品绑定匹配

- 根据订单的 `product_id`（GoodsId）查找绑定关系（`product_binding`）。
- 绑定配置决定发货内容类型：`card`（卡密池）/ `text`（固定文案）/ `link`（链接）/ `manual`（手动）。
- 本仓库 `storage.getProductBinding(shopId, productId)` 已实现；未绑定则记录 `no_binding` 日志并跳过。

### 需求 3：取发货内容

- `card`：从卡密池 `consumeCard(bindingId, orderId)` 消耗一张，池空则 `out_of_stock`。
- `text` / `link`：直接使用 `deliver_content`。
- `manual`：标记 `pending_manual`，等待人工。

### 需求 4：找买家并开聊（订单号 → chatId）

对标阿奇锁 `getUserByOrderSnChatId`（`XhsShopContext` 成员）与 `IMSend.js`：

1. `search_customer` 接口：`GET /api/edith/mcs/search_customer?seller_id=...&keyword=<orderSn>&page_no=1&page_size=5` → 得到买家 `id`。
2. `XhsRim.rimSdk.getChatInfo(arg1, arg2)` → 得到 `chatId`。

本仓库 `im-send.js` 已实现 `getUserByOrderSn` + `getChatId`。

**验收**：给定订单号，能拿到买家 ID 和 chatId；找不到买家时报明确错误。

### 需求 5：发送消息

- `XhsRim.sendTextMsg(content, { chatId })` 发送卡密/文案。
- 校验 `sendTextMsgResult.status === 'success'` 才算成功。
- 本仓库 `deliverByOrderSn(orderSn, content)` 一站式封装。

**验收**：成功发送后，买家在客服会话中收到对应内容；返回 `success=true` 及 `chatId`、`buyerId`。

### 需求 6：队列、去重与状态机

对标阿奇锁 `XhsMsgPool` + `OrderImMsgManager`：

- **去重**：`processedOrders` 集合，避免同一订单重复发货。
- **状态机**：`sending → success / fail`；`MessageRetryTask` 对失败订单重试。
- **发货日志**：每单记录 `shopId / orderId / trackingNumber / status / errorMsg`。
- 本仓库 `autoship.service.ts` 已有 `processedOrders` 与 `addShipLog`。

**验收**：同一订单只发一次；失败的能重试；日志可查。

### 需求 7：补发（售后/补发单）

对标 `AutoShipReshipConfig` + `MessageRetryTask` + `GetReissueMessagesAsync`：

- `autoreship.service.ts` 已实现补发监测，检测补发单后复用 `handleNewOrder` 流程。

## 六、遗留风险与待确认

1. **阿奇私有云 WS 协议**：`xhsmsgwebsocket.agiso.com` 的鉴权与消息格式（`AssistantImMsgRequest/Response`）未在本仓库完整实现，目前订单主要依赖「页面 API 轮询 + 拦截」，需确认是否必须接入云 WS。
2. **签名 `_webmsxyw`**：小红书页面签名算法可能随版本变化，需保证页面注入后该函数存在。
3. **IM 发送必须依赖页面 `XhsRim`**：若客服聊天页未打开或未加载完成，发货会失败（本仓库已做 `hasXhsRim` 检测）。

## 七、订单探测方式调研（轮询 vs 推送）

### 7.1 阿奇锁为何能「被动接收」订单

阿奇锁是**小红书开放平台（open.xiaohongshu.com）的 ISV 服务商**，其订单来源链路：

```
小红书开放平台「应用消息推送」能力
  （官方文档：支持商品、订单、售后关键业务节点的消息推送）
        ↓
阿奇锁服务商应用（已获得店铺授权 + access_token）
        ↓
订单事件 → 阿奇云服务 → WebSocket 推送到客户端（AssistantMessage）
```

**核心结论**：
1. **小红书官方本身有订单推送能力**（开放平台「应用消息推送」+ `order.getOrderList`/`getOrderDetail` 等正式 API），但这是**开放平台服务商能力**，需要：
   - 注册开放平台开发者账号
   - 创建应用（自营/ISV 服务商模式）
   - 商家授权店铺给应用（OAuth）
   - 成为付费服务商 / 满足开放平台门槛
2. **阿奇锁作为服务商付了钱/通过了门槛**，所以能拿到官方推送 + 正式 API。
3. **你选择纯本地免费方案**（直接注入客服页面，复用客服会话里的 Cookie/签名），不接开放平台，因此**没有官方推送**，只能**轮询探测**。

### 7.2 本地轮询方案（免费替代）

本仓库用三通道轮询/拦截替代官方推送：

| 通道 | 文件 | 机制 |
|---|---|---|
| 页面 API 轮询 | `im-send.js#fetchPendingOrders` | 定时调用 `fulfillment/order/page`（待发货列表） |
| 请求拦截 | `api-interceptor.js` | 拦截页面自发的 `fulfillment/order/page` 响应，被动捕获 |
| DOM 轮询 | `order-monitor.js` | 监听订单列表 DOM 变化 |

**这符合你的「纯免费」定位**：复用客服页已登录的 Cookie 和 `_webmsxyw` 签名，无需开放平台授权。

### 7.3 轮询频率设计（调研结论）

综合「及时性 vs 风控/资源占用」的平衡，参考业界自动发货工具（卡密商城、自动客服）的通用实践：

| 频率档 | 间隔 | 适用场景 | 建议 |
|---|---|---|---|
| 激进 | 5~10 秒 | 高并发店铺、秒发需求 | ⚠️ 频率过高有被限流/风控风险 |
| **推荐** | **15~30 秒** | **常规自动发货** | ✅ 平衡及时性与安全 |
| 保守 | 60 秒 | 低频店铺、纯补单 | 及时性略差 |

**推荐默认 30 秒**，理由：
1. 虚拟商品发货对「秒级实时」不敏感，买家下单后 30 秒内收到卡密可接受。
2. `fulfillment/order/page` 是内部接口，频率过高可能触发风控/限流（比开放平台 API 更敏感，因为它是"绕过"而非"授权"）。
3. 配合 `api-interceptor.js` 的「被动拦截」作为补充：用户手动刷新订单页时也能捕获，减少对轮询的依赖。

**建议实现**：
- 默认 `pollIntervalMs = 30000`（30 秒），可在配置里调整。
- 采用「固定间隔 + 抖动（jitter）」避免多实例同时请求：`interval + random(0~5s)`。
- 兜底：若一次轮询失败（网络/限流），指数退避重试（3s → 6s → 12s → 封顶 60s）。
