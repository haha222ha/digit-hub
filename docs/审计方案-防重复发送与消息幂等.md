# 审计方案：防重复发货 / 消息幂等（对标阿奇锁完整对齐）

> 目标：让 `xhs-shipping-assistant` 在「识别订单 → 自动发消息」链路中**不重复、不丢卡密、不崩溃丢状态**，与阿奇锁（Agiso）对齐。
> 依据：反编译阿奇锁 DLL 字符串（`tools/_agiso_strings/`）完整审计 + 本仓库源码逐行比对。

---

## 一、阿奇锁防重体系（已审计还原）

阿奇锁通过「**持久化订单消息表 + 唯一索引 + 状态机 + 消息级 GUID + 乐观锁重试**」五层机制保证不重复发送。反编译证据如下：

### 1.1 核心实体 `OrderImMsg` / `XhsOrderImMsg`

订单发货不是"发完即忘"，而是先落库成一条 `OrderImMsg` 记录，整个生命周期围绕这条记录状态机流转。

关键仓储方法（`Agiso.XhsClient.Core.Repositorys.OrderImMsgRepository`）：

| 方法 | 作用 |
|---|---|
| `CreateIndexAsync` | **创建唯一索引**（防重根基） |
| `GetByTidAsync` | 按订单号（Tid）查是否已存在 → **处理前判重** |
| `InsertBoolAsync` | 插入订单消息（唯一约束兜底） |
| `GetByMsgGuidAsync` | 按消息 GUID 查单条消息 |
| `UpdateStatusAsync` | 更新订单级状态 |
| `UpdateStatusByMsgGuidAsync` | **按消息 GUID 更新单条状态**（多轮精确追踪） |
| `GetFailedRetryableLogsAsync` | 查询「失败且可重试」的日志 |
| `IncrementRetryCountAsync` | 重试计数 +1（乐观锁） |
| `UpdateUidByTidAsync` | 按订单号回填买家 UID |
| `GetReissueMessagesAsync` | 查询需补发的消息 |
| `DisableOrderImMsgAsync` | 禁用/作废订单消息 |

### 1.2 消息级 GUID：`ImMsgGuids`

`AssistantImMsgRequest`（阿奇云下发指令）自带 `ImMsgGuids` —— 每条消息都有全局唯一 ID。这是「精确到单条消息」的幂等锚点。

### 1.3 状态机（`OrderImMsgManager`）

```
sending（发送中）──成功──▶ success（终态）
       │
       └──失败──▶ fail（终态，可重试）
```

对应方法：`SetReplySendingAsync` → `SetReplySuccessAsync` / `SetReplyFailAsync`。

### 1.4 重试乐观锁（关键 SQL，反编译还原）

```sql
UPDATE OrderImMsg
SET RetryCount = RetryCount + 1, ModifyTime = ?
WHERE IdNo = ?
  AND SendStatus = ?;          -- 仅当状态匹配才更新，条件不满足则 changes=0
```

通过 `WHERE SendStatus = ?` 的**乐观锁**，保证并发下只有一个执行体能改到该记录。

### 1.5 队列级去重：`ContainsShipmentInQueue`

入队前先检查「该订单是否已在发送队列中」，避免同一订单被重复入队。

### 1.6 补发机制：`GetReissueMessagesAsync` + `GetNeedReissuriOrderImMsg`

只补发「失败的订单消息」，成功的不再触碰 —— 这是「不重复发」的最后一道防线。

## 二、本仓库现状审计（差距分析）

逐行比对 `storage.service.ts` + `autoship.service.ts`，发现 **5 个防重缺陷**：

| # | 缺陷 | 现状代码 | 阿奇锁对应机制 | 风险等级 |
|---|---|---|---|---|
| 1 | **防重标记只在内存** | `private processedOrders: Set<string>`（`autoship.service.ts:17`） | `OrderImMsg` 表 + `IdNo` 唯一索引（持久化） | 🔴 严重 |
| 2 | **卡密无锁定态、无回滚** | `consumeCard` 直接 `unused→used`（`storage.service.ts:580`），失败不回收 | `locked` 中间态 + 失败回滚 `unused` | 🔴 严重 |
| 3 | **处理前无持久化判重** | 仅 `processedOrders.has()` 内存判断 | `GetByTidAsync` 查库判重 | 🔴 严重 |
| 4 | **无消息级 GUID / 状态机** | 只有 `ship_log` 一条日志，无单条消息状态 | `ImMsgGuids` + `UpdateStatusByMsgGuidAsync` | 🟡 中等 |
| 5 | **并发锁仅进程内** | `isShipping` 布尔（`autoship.service.ts:18`） | 乐观锁 `WHERE SendStatus=?` | 🟡 中等 |

### 2.1 缺陷 1 + 3 的后果（最严重）

```
场景：程序在「发消息成功、但 addShipLog 前」崩溃，或进程被强杀
→ processedOrders（内存）丢失
→ 重启后同一订单再次进入 handleNewOrder
→ 因为无持久化判重，重复发消息给买家
```

这正是阿奇锁用 `OrderImMsg` 表 + 唯一索引要解决的：**防重必须在数据库层，而非内存**。

### 2.2 缺陷 2 的后果

```
场景：consumeCard 消耗卡密 → executeRealShip 失败（IM 未就绪/网络超时）
→ 卡密已变 used，但买家没收到
→ 重试时又消耗下一张卡密
→ 卡密浪费 + 第一张卡密"幽灵占用"
```

阿奇锁方案：卡密/消息先「锁定」（`locked`），发送成功才「确认」（`used`），失败「回滚」（`unused`）。

## 三、对齐落地方案（本仓库改造设计）

### 3.1 新增持久化订单表 `order_delivery`（对标 `OrderImMsg`）

```sql
CREATE TABLE IF NOT EXISTS order_delivery (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  shop_id TEXT NOT NULL,
  order_id TEXT NOT NULL,           -- 对标阿奇锁 Tid/IdNo
  product_id TEXT,
  binding_id INTEGER,
  buyer_uid TEXT,                   -- 对标 UpdateUidByTidAsync
  msg_guid TEXT NOT NULL,           -- 消息级 GUID，对标 ImMsgGuids
  msg_index INTEGER DEFAULT 1,      -- 多轮第几条
  msg_total INTEGER DEFAULT 1,      -- 多轮共几条
  send_status TEXT DEFAULT 'pending', -- pending/sending/success/fail/disabled
  retry_count INTEGER DEFAULT 0,    -- 对标 RetryCount
  card_content TEXT,                -- 本单消耗的卡密（含 {uid} 动态码）
  error_msg TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);

-- 唯一索引：订单级幂等锚点（对标 CreateIndexAsync）
CREATE UNIQUE INDEX IF NOT EXISTS idx_order_delivery_order
  ON order_delivery(order_id);

-- 消息级唯一：对标 ImMsgGuids
CREATE UNIQUE INDEX IF NOT EXISTS idx_order_delivery_guid
  ON order_delivery(msg_guid);
```

**关键点**：`order_id` 的唯一索引是「永不重复发」的终极保证 —— 即使程序崩溃重启、即使多进程并发，数据库层直接拒绝重复插入。

### 3.2 卡密池引入「锁定」中间态（对标 locked 状态机）

```sql
-- card_pool.status 扩展为三态：unused / locked / used
```

`consumeCard` 拆成三段式（对标阿奇锁「锁定→确认→回滚」）：

```ts
// 1) 锁定（事务内，原子，防并发重复取）
lockCard(bindingId, orderId): string | null {
  return this.db.transaction(() => {
    const card = this.db.prepare(
      `UPDATE card_pool SET status='locked', order_id=?, locked_at=datetime('now')
       WHERE id = (SELECT id FROM card_pool WHERE binding_id=? AND status='unused' ORDER BY id LIMIT 1)
       RETURNING card_content`
    ).get(orderId, bindingId) as any
    return card?.card_content ?? null
  })()
}

// 2) 确认（发送成功后）
confirmCard(orderId): void {
  this.db.prepare(
    `UPDATE card_pool SET status='used', used_at=datetime('now') WHERE order_id=? AND status='locked'`
  ).run(orderId)
}

// 3) 回滚（发送失败后）
rollbackCard(orderId): void {
  this.db.prepare(
    `UPDATE card_pool SET status='unused', order_id=NULL WHERE order_id=? AND status='locked'`
  ).run(orderId)
}
```

### 3.3 发货主流程改造（对标 `AutoSendMsg` + 状态机）

```
handleNewOrder(order):
  1. 幂等拦截：INSERT OR IGNORE order_delivery(shop_id, order_id, ... status='pending')
     → changes=0 说明订单已存在（已发过/处理中）→ 直接 return，【防重核心】
  2. 绑定匹配：getProductBinding
  3. 构建消息：buildMessages → messages[]（多轮/多段）
  4. 逐条发送（状态机 + 消息级追踪）：
     for (i, msg) in messages:
       - 锁定卡密 lockCard（如含 {card}）
       - UPDATE order_delivery SET send_status='sending' WHERE msg_guid=?
       - executeRealShip(msg)
       - 成功：confirmCard + UPDATE send_status='success'
       - 失败：rollbackCard + UPDATE send_status='fail', error_msg=?
  5. 全部成功 → 订单终态 success
```

**对比旧流程**：旧流程 `processedOrders.add()` 在发货成功后加内存标记；新流程在**发货前**就通过 `INSERT OR IGNORE` 落库占位，从根本上杜绝并发/崩溃重复。

### 3.4 重试机制（对标 `MessageRetryTask` + 乐观锁）

```ts
// 启动时扫描 + 定时扫描「失败且可重试」的订单
getFailedRetryableLogs(limit): rows {
  return this.db.prepare(
    `SELECT * FROM order_delivery
     WHERE send_status='fail' AND retry_count < 3
     ORDER BY updated_at ASC LIMIT ?`
  ).all(limit)
}

// 重试时乐观锁抢占（对标 WHERE SendStatus=? 的乐观锁）
tryClaimRetry(id): boolean {
  const r = this.db.prepare(
    `UPDATE order_delivery
     SET retry_count=retry_count+1, send_status='sending', updated_at=datetime('now')
     WHERE id=? AND send_status='fail'`
  ).run(id)
  return r.changes === 1   // 只有抢占成功的执行体才继续发送
}
```

### 3.5 队列级去重（对标 `ContainsShipmentInQueue`）

保留内存队列，但增加「落库占位」后不再重复入队：

```ts
// 入队前检查
if (this.queue.has(orderId) || this.storage.existsDelivery(orderId)) return
this.queue.add(orderId)
```

### 3.6 断点续发（多轮消息防重发）

多轮对话部分失败时，利用 `msg_index` + `send_status` 只补发未成功的条，避免重复发已成功的条（对应 `GetReissueMessagesAsync`）：

```ts
getUnsentMessages(orderId): rows {
  return this.db.prepare(
    `SELECT * FROM order_delivery
     WHERE order_id=? AND send_status IN ('pending','fail')
     ORDER BY msg_index ASC`
  ).all(orderId)
}
```

## 四、防重核心原则总结（与阿奇锁一一对应）

| 阿奇锁机制 | 本仓库落地 | 防的问题 |
|---|---|---|
| `OrderImMsg` 表 + `IdNo` 唯一索引 | `order_delivery` 表 + `order_id` 唯一索引 | 订单重复发（含崩溃/重启/多进程） |
| `GetByTidAsync` 处理前判重 | `INSERT OR IGNORE` 落库占位 | 并发入队重复 |
| `ImMsgGuids` 消息级 GUID | `msg_guid` 字段 + 唯一索引 | 单条消息重复 |
| `locked` 卡密锁定态 | `card_pool.status='locked'` 三段式 | 卡密浪费 / 幽灵占用 |
| `SetReplySending/Success/Fail` 状态机 | `send_status` 状态机 | 状态不可知 / 无法重试 |
| `IncrementRetryCountAsync` 乐观锁 | `tryClaimRetry` 的 `WHERE send_status='fail'` | 并发重试竞争 |
| `ContainsShipmentInQueue` | 队列 + 落库双重检查 | 队列重复入队 |
| `GetReissueMessagesAsync` 补发 | `getUnsentMessages` 断点续发 | 多轮部分重复发 |

## 五、实施优先级

| 阶段 | 内容 | 风险消除 | 优先级 |
|---|---|---|---|
| P0 | 新建 `order_delivery` 表 + 唯一索引；`INSERT OR IGNORE` 幂等拦截 | 🔴 缺陷 1、3（崩溃重复发） | 最高 |
| P1 | 卡密 `locked` 三段式（锁定/确认/回滚） | 🔴 缺陷 2（卡密浪费） | 最高 |
| P2 | `send_status` 状态机 + `msg_guid` + 多轮追踪 | 🟡 缺陷 4（无法追踪） | 高 |
| P3 | `tryClaimRetry` 乐观锁重试 + 断点续发 | 🟡 缺陷 5（并发/重复） | 高 |
| P4 | 前端展示 `order_delivery` 状态 + 手动重试按钮 | 运维可观测 | 中 |

## 六、验收标准（防重专项）

1. **崩溃防重**：订单发消息成功后立即杀进程，重启后该订单不再重复发送。
2. **并发防重**：同一订单同时从两个通道（轮询 + 拦截）进入，只发送一次。
3. **卡密不浪费**：IM 发送失败后，该卡密回到 `unused`，可被下一单正常消耗。
4. **多轮断点续发**：3 条消息第 2 条失败，重试只补发第 2、3 条，第 1 条不重复。
5. **重试上限**：同一订单失败重试不超过 3 次，超过标记为需人工介入。
6. **状态可追溯**：任意订单可在 `order_delivery` 查到精确到每条消息的状态。

## 七、遗留风险

1. **IM 发送结果不确定性**：`XhsRim.sendTextMsg` 返回成功，但实际可能未送达（页面层无强一致回执）。阿奇锁同样依赖此回执，属平台能力边界，需接受「已发送但可能未达」的极小概率。
2. **多实例多机**：唯一索引仅保证单机数据库防重；若未来多设备同时登录同一店铺，需引入分布式锁或服务端去重（阿奇锁通过阿奇云服务端下发 `ImMsgGuids` 解决，本地化方案需权衡）。
3. **`{uid}` 动态码 vs 卡密锁定的关系**：`{uid}` 无卡密池，但复用 `card_content` 字段追溯，需确保回滚逻辑不影响 `{uid}` 场景。
