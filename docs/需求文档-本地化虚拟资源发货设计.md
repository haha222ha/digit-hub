# 需求文档：本地化虚拟资源自动发货系统设计（商品绑定 + 激活码/网盘链接自动发货）

> 目标系统：`xhs-shipping-assistant`（Electron + Vue3 + Element Plus + Pinia + SQLite）
> 对标参考：阿奇索 Agiso 自动发货（卡密池 + 自动采购 + 聊天窗发货范式）、kamiFaka 卡密商城（卡密状态机 + 随机发货 + 模板变量）
> 前置文档：本文是《需求文档-订单识别与自动发消息.md》的落地设计篇，聚焦「本地化界面 + 完整发货内容体系」

---

## 一、设计目标

不接入阿奇私有云，完全本地化。用户通过本地界面完成以下闭环：

```
① 绑定店铺商品（product_id）
② 为商品配置「发货内容策略」（激活码 / 网盘链接 / 文本模板 / 图片 / 视频 / 多段）
③ 系统自动识别新订单（订单号 + 商品ID）
④ 按策略取内容（消耗卡密 / 渲染模板）
⑤ 通过客服 IM 自动发给买家
⑥ 记录发货日志 + 库存/卡密状态管理
```

---

## 二、调研结论：成熟方案核心要素（可借鉴）

对标阿奇索 Agiso + kamiFaka 等行业成熟方案，虚拟商品自动发货系统的标准能力如下：

| # | 成熟要素 | 说明 | 本系统现状 |
|---|---|---|---|
| 1 | **卡密池（Card Pool）** | 批量导入、去重、状态机（未用/已用/锁定）、消耗时原子取卡 | ✅ 已有 `card_pool` 表 + `consumeCard` 事务 |
| 2 | **多发货类型** | 卡密/文本/链接/图片/视频/网盘提取码 | ⚠️ 仅有 card/text/link/manual |
| 3 | **模板变量（占位符）** | `{订单号}` `{买家昵称}` `{商品名}` `{卡密}` 等运行时替换 | ❌ 缺失 |
| 4 | **随机发货** | 卡密池随机抽取 / 文案随机多选一 | ❌ 缺失 |
| 5 | **库存告警** | 卡密池低于阈值时提示/停发 | ⚠️ 有 stock 字段但无告警 |
| 6 | **发货方式** | 聊天窗 IM 直接发 / 短信 | ✅ IM 已实现 |
| 7 | **订单-卡密追溯** | 每张卡密关联订单号，可查 | ✅ `order_id` 字段已实现 |
| 8 | **失败重试 + 补发** | 发送失败重试、缺货标记 | ✅ 补发服务已实现 |
| 9 | **内容分组/多段消息** | 一段商品发多条消息（如：网盘链接 + 提取码 + 教程） | ❌ 缺失 |

**结论**：你的系统底子已达行业 60% 水平，缺口集中在「内容类型丰富度 + 模板变量 + 随机发货 + 库存告警 + 多段消息」这五项。以下设计补齐这些能力，并与现有代码**无缝对接**（复用现有表结构和 IPC 通道）。

## 三、核心设计：发货内容策略（Deliver Policy）

### 3.1 概念模型

现有 `product_bindings.deliver_type` 从 4 种扩展为 **6 种发货类型**，并引入「多段消息」能力：

```
deliver_type ∈ { card, text, link, image, video, mixed, manual }
```

| 类型 | 值 | 含义 | 内容来源 |
|---|---|---|---|
| 激活码/卡密 | `card` | 从卡密池消耗一张 | `card_pool` |
| 固定文本 | `text` | 固定文案（支持占位符） | `deliver_content` |
| 网盘链接 | `link` | 固定链接（支持占位符） | `deliver_content` |
| 图片 | `image` | 发一张图片 | `deliver_content`（URL 或本地路径） |
| 视频 | `video` | 发一个视频 | `deliver_content` |
| 多段组合 | `mixed` | 依次发多条消息 | `deliver_content`（JSON 数组） |
| 手动 | `manual` | 人工发货 | — |

### 3.2 模板变量（占位符）系统 —— 关键新增能力

这是本次设计最重要的新增项。`deliver_content` 支持占位符，运行时替换：

| 占位符 | 含义 | 数据来源 |
|---|---|---|
| `{order_id}` / `{订单号}` | 订单号 | 订单识别结果 |
| `{buyer_name}` / `{买家昵称}` | 买家昵称 | `search_customer` 返回 |
| `{product_name}` / `{商品名}` | 商品名称 | `product_bindings.product_name` |
| `{card}` / `{卡密}` | 本次消耗的卡密 | `consumeCard` 返回 |
| `{shop_name}` / `{店铺名}` | 店铺名称 | 店铺上下文 |

**替换时机**：在 `processShipment` 拿到最终 `deliverContent` 后、`executeRealShip` 发送前，调用 `renderTemplate(content, context)` 完成替换。

**示例**：网盘链接发货
```
deliver_content = "您好，感谢购买！\n网盘链接：https://pan.xxx.com/s/ABC123\n提取码：{card}"
```
当绑定类型为 `card` 时，`{card}` 会被替换为实际消耗的卡密；若用 `text` 类型，则 `{card}` 也可用（配合卡密池，见 3.4）。

### 3.3 多段消息（mixed 类型）

`deliver_content` 存 JSON 数组，依次发送：

```json
[
  { "type": "text", "content": "您好，{买家昵称}，感谢购买【{商品名}】" },
  { "type": "link", "content": "https://pan.xxx.com/s/ABC123" },
  { "type": "text", "content": "提取码：{card}" },
  { "type": "image", "content": "https://img.xxx.com/tutorial.png" }
]
```

每段独立发送，全部成功才算订单发货成功；任一段失败则该段可重试。

### 3.4 随机发货（可选开关）

在 `product_bindings` 新增 `random_mode` 字段（0/1）：
- 卡密：`consumeCard` 从 `ORDER BY id ASC` 改为 `ORDER BY RANDOM()`（随机消耗）。
- 文案：`deliver_content` 支持 `\n---\n` 分隔多组随机文案，发货时随机选一组。

### 3.5 动态链接卡密（链接模板 + 参数拼接）—— 本次新增

**场景**：卡密本身是一条「带参数的链接」，而非固定字符串。常见于：
- 网盘/资源站直链：`https://pan.xxx.com/s/` + 每单不同的提取码/短链
- 兑换链接：`https://shop.xxx.com/redeem?code=` + 每单唯一的激活码
- 追踪链接：`https://xxx.com/d/{订单号}`（参数带订单号做统计归因）

**方案**：引入「链接模板 + 参数策略」模式，与占位符系统天然融合。在 `deliver_content` 中直接书写链接模板，参数用占位符表示，发货时拼接成最终完整链接。

#### 3.5.1 支持的参数来源（占位符）

| 参数占位符 | 含义 | 生成方式 |
|---|---|---|
| `{card}` | 从卡密池消耗一张（如提取码、激活码） | `consumeCard` 原子消耗 |
| `{order_id}` | 订单号（做归因/追踪） | 订单识别结果 |
| `{uid}` | 随机唯一短码（每单唯一，防复用） | 运行时随机生成 |
| `{ts}` | 时间戳（做防缓存/签名） | 运行时生成 |

#### 3.5.2 配置示例

**示例 A：网盘直链 + 提取码**
```
发货类型：card
发货内容（模板）：https://pan.xxx.com/s/ABC123 提取码：{card}
```
发货时 → `https://pan.xxx.com/s/ABC123 提取码：5F3K-8Q2Z`

**示例 B：纯链接 + 动态码（卡密就是完整链接的尾参数）**
```
发货类型：card
发货内容（模板）：https://shop.xxx.com/redeem?code={card}
```
发货时 → `https://shop.xxx.com/redeem?code=J8X2-P4KD-9Q1L`

**示例 C：订单归因追踪链接**
```
发货类型：link
发货内容（模板）：https://xxx.com/d/{order_id}
```
发货时 → `https://xxx.com/d/20260813XXXX12345`

**示例 D：随机唯一短码（无卡密池，每次生成新码）**
```
发货类型：text
发货内容（模板）：https://xxx.com/gift?key={uid}
```
发货时 → `https://xxx.com/gift?key=A9K3F7X2Q1`（`{uid}` 每次随机生成，保证每单唯一）

#### 3.5.3 生成规则

1. `{uid}` 随机短码：默认 8~12 位大小写字母+数字（如 `A9K3F7X2Q1`），生成后写入 `ship_log` 的 `card_content` 字段以便追溯；长度可在绑定配置中设置（`uid_length`，默认 10）。
2. `{ts}` 时间戳：13 位毫秒时间戳。
3. 拼接顺序：先 `renderTemplate` 替换所有占位符（含 `{card}`/`{uid}`/`{ts}`/`{order_id}`），得到最终完整链接字符串，再作为消息内容发送。
4. 当模板含 `{card}` 时，走卡密池消耗（锁定→确认→回滚）；当模板只含 `{uid}`/`{ts}` 时，无需卡密池，直接生成。

#### 3.5.4 数据模型影响

- `product_bindings` 新增 `uid_length INTEGER DEFAULT 10`（`{uid}` 随机码长度）。
- 无需新表；`{uid}` 生成结果复用 `ship_log.card_content` 字段存储（当前该字段语义为「发货卡密内容」，动态码等同卡密内容）。
- `renderTemplate` 增加对 `{uid}`、`{ts}` 的处理：`{uid}` 在函数内按 `uid_length` 生成，`{ts}` 取当前毫秒。

### 3.6 多轮对话（分隔符切分多条消息）—— 对标阿奇锁

**来源**：阿奇锁反编译审计确认，其多轮对话模型为：

- `AssistantImMsgRequest` 含 `ImMsgs`（消息**数组**）+ `SendMsgInterval`（每条消息发送间隔）。
- `XhsSendMsg` / `XhsImMsg` 是单条消息实体，`imMsgList` / `orderImMsgList` 是消息列表。
- `ConvertToXhsSendImMsg` 将用户配置内容转换为「待发送消息列表」，客户端按 `SendMsgInterval` 间隔依次发送。

即：**用户在配置里用「分隔符」书写多条消息 → 客户端按分隔符拆分成 `ImMsgs` 列表 → 按间隔依次发送**。这与本文 3.3 的 `mixed`（JSON 数组）互补：分隔符方案面向「纯文本多轮」，更轻量、更贴近用户书写习惯；`mixed` 面向「图文混排多类型」。

#### 3.6.1 分隔符设计

采用「双换行」为主分隔符 + 可选自定义分隔符，兼容阿奇锁的书写范式：

| 分隔符 | 写法 | 说明 |
|---|---|---|
| 双换行（默认） | 两条消息之间空一行 | 最直观，用户敲一次回车空行即切分 |
| 自定义分隔符 | 如 `\n---\n`、`\n|||\n` | 在绑定配置里指定 `msg_separator` |

**配置示例（文本多轮对话）**：
```
发货类型：text
发货内容（模板）：
您好，{买家昵称}，感谢购买【{商品名}】～    ← 第 1 条
                                             ← （空行 = 分隔符）
您的网盘链接：https://pan.xxx.com/s/ABC123    ← 第 2 条
                                             ← （空行 = 分隔符）
提取码：{card}                                ← 第 3 条
```
发货时按顺序依次发送 3 条消息，间隔 `send_interval_ms`。

**与动态链接卡密组合示例**：
```
发货类型：card
发货内容（模板）：
下单成功，这是您的专属链接👇              ← 第 1 条

https://shop.xxx.com/redeem?code={card}    ← 第 2 条（动态链接）

使用遇到问题请回复本消息～                ← 第 3 条
```

#### 3.6.2 拆分与发送规则

1. **拆分时机**：在 `buildMessages` 阶段，`text` / `link` / `card` 类型若 `deliver_content` 含分隔符，则拆成多条消息；`mixed`（JSON 数组）与 `image`/`video`（单条）不走分隔符拆分。
2. **拆分算法**：优先按自定义 `msg_separator`（若配置），否则按 `\n\n`（连续换行）切分；切分后 `trim` 去掉首尾空白，过滤空片段。
3. **模板渲染顺序**：先拆分成多条，再逐条 `renderTemplate` 替换占位符（保证 `{card}` 只在含它的那一条被消耗一次）。
4. **发送顺序**：严格按第一条 → 第二条 → ... 依次发送，每条间隔 `send_interval_ms`（默认 500ms），模拟真人逐条发送节奏。
5. **状态判定**：所有条全部发送成功 → 订单标记 success；任一条失败 → 该订单标记 fail（可整体重试；已成功发送的前置条不重复发，通过 `ship_log` 记录每条进度）。
6. **卡密消耗**：`{card}` 只出现在一条消息中，消耗一次；若配置错误在多条出现 `{card}`，仅第一条消耗卡密，其余条 `{card}` 替换为同一张卡密内容（同一订单同一卡密）。

#### 3.6.3 数据模型影响

- `product_bindings` 新增 `msg_separator TEXT DEFAULT '\n\n'`（自定义分隔符，默认双换行）。
- 复用已有 `send_interval_ms` 字段控制发送间隔（见 4.1）。
- `ship_log` 新增 `msg_index`（第几条）与 `msg_total`（共几条）字段，用于多轮进度追踪与失败重试定位。
- 与 3.3 `mixed` 的关系：`msg_separator` 仅对纯文本类型生效；`mixed` 用 JSON 数组表达，两者互斥，界面按发货类型切换。

### 5.2 核心流程改造（processShipment）

```
processShipment(shopId, order):
  1. binding = storage.getProductBinding(shopId, product_id)
  2. if !binding → log('no_binding'), return false
  3. messages = buildMessages(binding, order)   # 见 5.3
  4. for each msg in messages:
       content = template.render(msg.content, context)  # 占位符替换
       if msg.type == 'card' → card = consumeCard(...)  # 锁定
       result = executeRealShip(order_id, msg)
       if fail → 回滚 card, 记录 failed, return false
       else → 确认 card 已用
  5. log('success'), return true
```

### 5.3 buildMessages 逻辑

```
buildMessages(binding, order):
  switch binding.deliver_type:
    'card'   → [{ type:'text', content:'{card}' }]  # 卡密作为文本发
    'text'   → [{ type:'text', content: deliver_content }]
    'link'   → [{ type:'text', content: deliver_content }]
    'image'  → [{ type:'image', content: deliver_content }]
    'video'  → [{ type:'video', content: deliver_content }]
    'mixed'  → JSON.parse(deliver_content)  # 多段
    'manual' → 标记 pending_manual
```

### 5.4 模板渲染服务（template.service.ts）

```ts
// 纯函数，无副作用
export function renderTemplate(content: string, ctx: {
  orderId: string
  buyerName?: string
  productName?: string
  card?: string
  shopName?: string
  uidLength?: number       // {uid} 随机码长度，默认 10
}): string {
  const uid = ctx.card ?? genUid(ctx.uidLength ?? 10)   // 有卡密用卡密，无卡密生成随机码
  const ts = Date.now().toString()
  return content
    .replace(/\{(订单号|order_id)\}/g, ctx.orderId)
    .replace(/\{(买家昵称|buyer_name)\}/g, ctx.buyerName || '')
    .replace(/\{(商品名|product_name)\}/g, ctx.productName || '')
    .replace(/\{(卡密|card)\}/g, ctx.card || '')
    .replace(/\{(店铺名|shop_name)\}/g, ctx.shopName || '')
    .replace(/\{uid\}/g, uid)
    .replace(/\{ts\}/g, ts)
}

function genUid(len: number): string {
  const chars = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'  // 去除易混淆字符 I/O/0/1
  let s = ''
  for (let i = 0; i < len; i++) s += chars[Math.floor(Math.random() * chars.length)]
  return s
}
```

### 6.1 页面结构（Shipping.vue 改造）

保留现有三个 Tab，重构为更完整的「发货管理」界面：

```
发货管理

```
买家下单
   │

## 八、验收标准（AC）

1. **商品绑定**：可绑定 6 种发货类型，内容支持 5 种基础占位符 + `{uid}`/`{ts}` 动态参数，保存后可回显编辑。
2. **卡密池**：批量导入自动去重（提示重复数）；随机/顺序消耗可配置；每张卡密能追溯订单号。
3. **模板渲染**：`{订单号}` `{买家昵称}` `{商品名}` `{卡密}` `{uid}` `{ts}` 在发货时正确替换；`{卡密}` 配合卡密池消耗。
4. **网盘链接发货**：`link` 类型 + `{卡密}` 占位符 → 买家收到「链接 + 提取码」完整内容。
5. **动态链接卡密**：链接模板尾参数拼接 `?code={card}` / `?key={uid}` / `?o={order_id}`，发货时生成完整可访问链接；`{uid}` 每次生成唯一随机码且写入发货日志可追溯。
6. **多段消息**：`mixed` 类型依次发送多段，全部成功才标记订单成功。
7. **多轮对话**：文本内容用「空一行」分隔符自动拆成多条，严格按顺序、按 `send_interval_ms` 间隔依次发送；`{卡密}` 只在含它的那一条消耗一次；部分失败可定位到具体第几条并整体重试。
8. **图片/视频**：`image`/`video` 类型通过 XhsRim 正确发送。
9. **库存告警**：库存低于阈值时前端出现告警提示；缺货订单记录 `out_of_stock`。
10. **失败重试**：IM 发送失败 → 卡密自动回滚为未用 → 可在发货记录手动重试。
11. **向后兼容**：现有 4 种类型（card/text/link/manual）行为不变，老数据无需迁移。

## 十、风险与注意

1. **XhsRim 能力边界**：图片/视频发送依赖页面 `XhsRim.sendImageMsg/sendCustomMsg` 是否可用，需在真实客服页验证（阿奇锁 IMSend.js 已证明 `sendImageMsg`、`sendCustomMsg(content_type:73/92)` 存在）。
2. **模板变量与卡密耦合**：`{card}` 占位符只在 `card` 类型或显式启用卡密池时有效，需在界面做约束提示。
3. **并发安全**：`consumeCard` 的「锁定-确认-回滚」必须在 SQLite 事务内完成，避免多订单并发取到同一张卡密。
4. **`mixed` 内容校验**：`JSON.parse(deliver_content)` 失败时需优雅降级为单段文本，避免发货崩溃。
5. **`{uid}` 唯一性**：随机短码存在极小概率碰撞，如需严格唯一（如兑换链接），应优先用 `{card}`（卡密池天然去重）而非 `{uid}`；`{uid}` 适用于「无需严格唯一、仅需每单可区分」的追踪/防缓存场景。
6. **链接参数编码**：拼接链接时，若卡密/参数含特殊字符（如 `&`、`?`、空格），需用 `encodeURIComponent` 编码，避免链接被截断失效。
7. **多轮拆分歧义**：若消息正文本身需要保留空行（如排版），会被误拆；需支持「自定义分隔符」（`msg_separator`）绕过，或用 `mixed` JSON 数组精确表达。
8. **多轮失败重试语义**：部分消息已发送成功、后续失败时，重试应只补发未成功的后续条（`ship_log.msg_index` 定位），而非从头重发导致买家收到重复内容；需在重试逻辑中明确「断点续发」。

## 十一、按订单号查询发卡 / 发卡记录管理（对标阿奇锁 OrderImMsgController）

### 11.1 需求背景

阿奇锁支持在「官网/后台」输入小红书订单号，即可查询该订单的发卡情况（发货了没、发的哪张卡密/哪个链接、状态如何），并支持**重发**、**作废**、**手动补发**等操作。反编译审计还原其实现本质：

- `AgisoXhsClient.Api.Controllers.OrderImMsgController` + `BaseOrderImMsgController<2>` —— 订单消息管理 API 控制器
- 内嵌 API：`[AgisoAppHost] API 已启动 http://localhost:` + Swagger（`/swagger/{documentName}/swagger.json`）
- 仓储层 `OrderImMsgRepository`：`GetByTidAsync`（按订单号查发卡）、`GetByIdAsync`、`GetListAsync`、`DisableOrderImMsgAsync`（作废）

**关键中文提示语（反编译还原的操作语义）：**

| 提示语 | 对应能力 |
|---|---|
| `请选择要重发的记录` / `成功添加 N 条消息到发送队列` | 手动重发（重新入队） |
| `发货消息不存在` / `消息不存在` | 按订单号/ID 查询未命中 |
| `手动作废` / `作废成功` / `消息已作废，无法重发` | 作废（禁止重发） |
| `查询成功` / `获取成功` / `更新成功` | CRUD 通用回执 |

**结论**：阿奇锁的「官网查询发卡」= **本地内嵌 HTTP API + Swagger + 订单消息仓储**，通过 `GET /api/OrderImMsg?tid={订单号}` 类接口，实现按订单号检索发卡记录与二次操作。

### 11.2 本仓库落地方案

你已有 `api.service.ts`（本地 `127.0.0.1:19527` + Swagger），**只需补充「订单发卡管理」这组接口**，并对应 `order_delivery` 表（见《审计方案-防重复发送与消息幂等.md》）。

#### 11.2.1 新增 API 接口（对标 BaseOrderImMsgController）

| 方法 | 路径 | 功能 | 对标阿奇锁 |
|---|---|---|---|
| GET | `/api/orders/deliveries` | 按订单号/商品/状态筛选查询发卡记录列表 | `GetByTidAsync` / `GetListAsync` |
| GET | `/api/orders/deliveries/:orderId` | 按订单号查单笔发卡详情（含卡密内容、消息状态） | `GetByTidAsync` |
| POST | `/api/orders/deliveries/:orderId/resend` | 手动重发（重新加入发送队列） | `OnResendMessageAsync` |

**关键交互**：
- 卡密内容默认脱敏显示（`https://pan... 提取码：5F3K-****`），点击「复制」才复制完整内容。
- 「重发」按钮仅对 `fail` 状态可用；`success` 状态不可重发（防重复）；`disabled` 状态灰显。
- 「作废」需二次确认，作废后卡密回滚为 `unused`（可选：作废同时回收卡密）。

#### 11.2.4 与防重体系的关系

- 查询/重发/作废全部围绕 `order_delivery` 表（`order_id` 唯一索引）进行，天然与《审计方案》的幂等体系一致。
- 「重发」走同一 `handleNewOrder` → `INSERT OR IGNORE` 逻辑，但因订单已存在，需走「断点续发」路径（`getUnsentMessages` 只补发失败条），而非重新插入。
- 「作废」将 `send_status` 置为 `disabled`，并可选回滚已锁定卡密。

#### 11.2.5 验收标准

1. 输入存在的订单号 → 返回该订单完整发卡记录（卡密内容、状态、时间）。
2. 输入不存在的订单号 → 返回明确提示「发货消息不存在」。
3. 对 `fail` 状态订单点「重发」→ 重新入队并发送，且不重复发已成功条。
4. 对 `success` 状态订单，「重发」按钮禁用。
5. 「作废」后，该订单无法再重发，提示「消息已作废，无法重发」。
6. 卡密内容在前端默认脱敏，复制时还原完整内容。

#### 11.2.6 数据模型影响

- 复用 `order_delivery` 表（见审计方案 3.1），无需新表。
- `send_status` 枚举增加 `disabled`（作废态）。
- 卡密 `card_content` 字段已存储，直接用于查询展示；脱敏在前端完成。
